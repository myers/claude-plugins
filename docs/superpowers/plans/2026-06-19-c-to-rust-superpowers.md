# `c-to-rust-superpowers` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the C→Rust port workflow as one plugin — an orchestration spine that rides the superpowers ladder, the translation method, and a fresh-context faithful-port reviewer template — by building the new content under cold-RED validation and relocating the two existing skills into it.

**Architecture:** Create a new plugin `plugins/c-to-rust-superpowers/` holding three skills. Two skills (`c-to-rust-port`, `faithful-port-review`) move in unchanged-in-substance from their current standalone plugins; one skill (`c-to-rust-superpowers`, the spine) is new, plus a new reviewer prompt template `faithful-port-reviewer.md`. The marketplace manifest collapses two entries into one and the README table is regenerated from it.

**Tech Stack:** Claude Code plugins (Markdown SKILL.md + JSON manifests). `scripts/gen_readme.py` (Python 3) regenerates the README plugin table from `.claude-plugin/marketplace.json`. No application code, no runtime dependencies.

## Global Constraints

- **This is a skill-authoring build under the `superpowers:writing-skills` Iron Law: no skill change without a failing test first.** The "test" for a skill is a **cold-RED validation artifact** — an out-of-repo, renamed, no-confession port artifact with a planted defect whose answer is NOT grep-reachable in this repo. RED = a fresh subagent given only the artifact + the skill/template fails to catch the planted defect (or a clean artifact gets false-flagged). GREEN = after the skill edit, the subagent catches the planted defect AND maps it to the right divergence class, and a clean artifact passes. (Spec: `docs/superpowers/specs/2026-06-19-c-to-rust-superpowers-build-design.md`, "Build discipline".)
- **Do not fork or edit superpowers' own SKILL.md files** — the spine delegates by name, never edits `plugins/myers-superpowers/` or the vendored superpowers cache.
- **Do not merge porter and reviewer into one context.** The reviewer template receives `{DIFF}` + `{C_REFERENCE_MAPPING}` only — never the porter's prose/rationale.
- **Do not duplicate the divergence taxonomy** (the three classes) into `c-to-rust-port`; it lives only in `faithful-port-review`.
- **Do not fold `rust-correctness-by-construction` into this plugin** — it stays its own plugin and its marketplace entry is untouched.
- **Plugin manifest values:** `name` `c-to-rust-superpowers`, `version` `1.0.0`, `author` `{ "name": "Myers Carpenter", "email": "myers@maski.org" }`.
- **Versioning (project CLAUDE.md):** new plugin starts at `1.0.0`.
- **README is autogenerated** by `scripts/gen_readme.py` from `marketplace.json`; never hand-edit the table between the `<!-- BEGIN PLUGINS -->`/`<!-- END PLUGINS -->` markers — edit `marketplace.json` and regenerate.
- **Git (user CLAUDE.md):** stage explicit filenames, never `git add .`. Develop on `main`. Use `git mv` to preserve history when relocating skills.

- The unifying insight verbatim in spirit: *every mode = (an entry generates a work-list) → (per item: faithful fix + prove + the faithful-port-reviewer gate) → confirm; only the entry differs.*
- The rung delegation (names only — DELEGATE, never fork): `superpowers:brainstorming → superpowers:writing-plans` (shaped by the sibling `c-to-rust-port` skill) `→ superpowers:subagent-driven-development` (TDD inside) `→ the faithful-port-reviewer gate (mandatory) → superpowers:finishing-a-development-branch`.

  - `remediate`: SWEEP (faithful-port-review sweep + method-gap pass) → TRIAGE + ORACLE-SEQUENCE (bucket: fix-now-has-live-oracle / cheap-safe / latent-or-gated; **do NOT fix what you can't validate**) → per finding: c-to-rust-port fix via SDD → faithful-port-reviewer gate → RE-SWEEP → finishing.

It does not replace code-quality review.
- The **anchor-harvest handoff (D3)**: the implementer writes `// C: <fn>() <label>:` anchors as it ports; the controller harvests `{C_REFERENCE_MAPPING}` from the task diff (grep the anchors) and fills the reviewer template; the reviewer never gets the porter's prose.
- A "Relationship" section: this skill = lifecycle/orchestration; `c-to-rust-port` = method; `faithful-port-review` = the check; `rust-correctness-by-construction` (separate plugin) = type catalog for the idiomatic phase. Layering analogy: `c-to-rust-superpowers : c-to-rust-port :: subagent-driven-development : test-driven-development`.

`faithful-port-reviewer.md`, modeled on superpowers' `requesting-code-review/code-reviewer.md`. Contents:

  - A "Read-only review" clause (mirror code-reviewer.md: do not mutate working tree/index/HEAD).
- A placeholders list under the fence (what each `{...}` is and where the controller gets it — note `{C_REFERENCE_MAPPING}` is harvested from `// C:` anchors in the diff).

## Notes for the executor

- **Cold-RED is the test discipline here.** Tasks 1–3 each have a real RED step (a fresh subagent fails *before* the skill/template exists) and a GREEN step (catches the planted defect AND maps it to the right class/gap, plus a clean-artifact regression). Do not skip RED — a skill edit you didn't watch fail first is unvalidated. Keep the ANSWER key out-of-repo so the subagent can't grep it.
- **Tasks 4–6 are mechanical** (move/manifest/docs); they have verification steps but not cold-RED, because they change no skill judgment.
- **Ordering rationale:** the new cold-RED-validated content (spine, template, method-gaps) is built first at provisional paths, then the existing skills are moved in around it, then the manifest/README catch up. Task 3 edits `faithful-port-review` at its *original* path and Task 4 moves it — if you reorder, adjust the path.
